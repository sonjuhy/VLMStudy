# 순수 ViT vs Depth ViT: CV-Bench 공간 이해 비교 실험 리포트

> 작성일: 2026-11-13
> 코드: [`depth_ab_study/cvbench/`](../depth_ab_study/cvbench/)
> 결과: [`depth_ab_study/results_cvbench/`](../depth_ab_study/results_cvbench/)

---

## 0. 요약

| 항목 | 내용 |
|---|---|
| 질문 | ViT 인코더에 **depth 채널(RGB-D)** 을 추가하면 VLM의 공간 이해 능력이 좋아지는가? |
| 평가 | 공인 벤치마크 **CV-Bench** (Cambrian-1, NeurIPS 2024) test 2,638문항 |
| 비교 | 순수 ViT(RGB, 3채널) vs Depth ViT(RGB-D, 4채널). 나머지 조건은 모두 같음 |
| 반복 | 인코더당 **seed 8개**, 총 16회 학습 |
| 결과 | CV-Bench 점수 **RGB 66.20 ± 0.72 → RGB-D 68.43 ± 1.21 (Δ +2.23)**. 무작위로 찍을 때 점수는 42.49 |
| 유의성 | Welch t-test **p = 0.0008**, seed·문항을 함께 재표집한 bootstrap 95% CI **[+0.75, +3.73]**. 차이가 오차 범위를 벗어남 |
| 핵심 | 효과는 과제마다 다름. **Depth(카메라 거리) +6.6, Relation(위치 관계) +4.1, nuScenes(실외) +6.2** 는 유의함. Count, Distance, Hypersim은 차이 없음 |

**결론**: depth 채널을 넣으면 CV-Bench 점수가 통계적으로 유의하게 오른다. 향상분은 "카메라 기준 거리 판단"과 "학습에 없던 분포(실외 장면)"에 몰려 있다. 개수 세기와 물체 간 3D 거리 추정에는 효과가 없다.

## 1. 용어 설명

### 1.1 모델 구성 요소

| 용어 | 설명 |
|---|---|
| **ViT (Vision Transformer)** | 이미지를 16×16 픽셀 조각(**패치**)으로 잘라 각 조각을 토큰처럼 다루는 Transformer 이미지 인코더. 224×224 이미지 한 장은 14×14 = **196개 패치 토큰**이 된다. 이 실험은 ViT-Base/16(12층, 768차원, 약 86M 파라미터)을 쓴다. |
| **순수 ViT (RGB 인코더)** | 일반 컬러 이미지(빨강·초록·파랑 3채널)를 입력받는 ViT. ImageNet-1K 분류로 직접 학습했다(Top-1 78.82%). |
| **Depth ViT (RGB-D 인코더)** | RGB 3채널에 **depth(깊이) 채널** 1개를 더한 4채널 입력 ViT. depth 맵은 픽셀마다 카메라에서 얼마나 먼지를 나타내는 흑백 이미지다. RGB와 같은 레시피로 ImageNet-1K를 학습했다(Top-1 70.58%). |
| **DA3 (Depth Anything 3)** | 사진 한 장에서 depth 맵을 추정하는 공개 단안(monocular) 깊이 추정 모델. 여기서는 `depth-anything/da3mono-large`를 쓴다. 센서로 잰 값이 아니라 **모델이 추정한 값**이다. |
| **VLM (Vision-Language Model)** | 이미지와 텍스트를 함께 입력받아 텍스트로 답하는 모델. 구조는 **이미지 인코더 → Projector → LLM** 이다(LLaVA 방식). |
| **LLM (Large Language Model)** | 텍스트를 이해하고 생성하는 언어 모델. 여기서는 **Qwen2.5-0.5B-Instruct**(약 5억 파라미터, hidden 896차원)를 쓴다. |
| **Projector** | ViT 출력(768차원)을 LLM 입력 공간(896차원)으로 바꾸는 작은 신경망. 여기서는 2층 MLP(Linear → GELU → Linear, **약 1.49M 파라미터**)다. 이미지와 언어를 잇는 "번역기" 역할을 한다. |
| **Frozen (동결)** | 학습 중 가중치를 바꾸지 않고 고정하는 것. 이 실험에서는 ViT와 LLM을 모두 동결하고 **Projector만 학습**한다. 그래야 두 인코더가 가진 정보의 차이만 비교할 수 있다. |
| **로짓(logit) / argmax 채점** | 로짓은 LLM이 다음 토큰 후보마다 매기는 점수다. 정답 보기 문자(A, B, C …) 중 로짓이 가장 큰 것(argmax)을 모델의 답으로 본다. 생성 문장을 파싱할 필요가 없어 채점이 결정적이다. |

### 1.2 벤치마크와 데이터셋

| 용어 | 설명 |
|---|---|
| **벤치마크** | 여러 모델을 같은 기준으로 비교하려고 공개해 둔 표준 시험 문제. |
| **CV-Bench** | Cambrian-1 논문(NeurIPS 2024)이 공개한 VLM용 시각 중심(vision-centric) 벤치마크. 기존 비전 데이터셋의 사람 주석과 3D 주석으로 **2,638개 객관식 문항**을 만들었다. 2D 1,438문항, 3D 1,200문항이다. |
| **Count (2D)** | "이미지에 ○○가 몇 개 있나?" 보기 4~6개. |
| **Relation (2D)** | "빨간 박스의 A가 B의 왼쪽/오른쪽(또는 위/아래) 중 어디에 있나?" 보기 2개. |
| **Depth (3D)** | "빨간 박스 물체와 파란 박스 물체 중 **카메라에 더 가까운** 것은?" 보기 2개. |
| **Distance (3D)** | "빨간 박스 물체에 **실제 3D 거리로 더 가까운** 것은 파란 박스와 초록 박스 중 무엇인가?" 보기 2개. |
| **ADE20K** | 실내·실외 장면 분할 데이터셋. CV-Bench 2D 문항 633개의 출처다. 학습에는 쓰지 않았다. |
| **COCO** | 일상 사진 물체 검출 데이터셋. CV-Bench 2D 문항 805개는 **val2017**에서, 이 실험의 학습 문항은 **train2017**에서 가져왔다. |
| **Omni3D** | 여러 3D 데이터셋을 하나로 묶은 3D 물체 검출 벤치마크. CV-Bench 3D 문항의 출처이며 아래 세 데이터셋에서 400문항씩 뽑았다. |
| **SUN RGB-D** | 실내 RGB-D 센서 데이터셋으로 3D 박스 주석이 있다. 학습 문항은 **공식 train split**(5,285장)에서 만들었다. CV-Bench SUN 문항과 이미지가 겹치지 않음을 코드로 확인했다. |
| **Hypersim** | 사실적으로 렌더링한 **합성 실내** 장면 데이터셋. 학습에는 쓰지 않았다. |
| **nuScenes** | 자율주행 차량이 찍은 **실외 도로** 장면 데이터셋. 학습에는 쓰지 않았다. |

### 1.3 실험 설계 용어

| 용어 | 설명 |
|---|---|
| **A/B 실험** | 한 가지 조건만 바꾸고(여기서는 인코더) 나머지를 모두 같게 둔 비교 실험. |
| **학습셋 / 검증셋(val) / 테스트셋(test)** | 학습셋은 모델을 학습시키는 데이터다. 검증셋은 학습 도중 상태를 확인하는 데이터로, 학습셋에서 3%를 떼어냈다. 테스트셋은 마지막에 **딱 한 번** 보는 최종 시험으로, 여기서는 CV-Bench다. |
| **in-domain / out-of-domain** | in-domain은 학습 데이터와 같은 분포의 데이터(예: SUN RGB-D 학습 → SUN 테스트)다. out-of-domain은 학습에서 본 적 없는 분포의 데이터(예: 실외 nuScenes)다. |
| **데이터 누출(data leakage)** | 정답을 만드는 데 쓴 정보가 모델 입력에도 들어가 실제보다 성능이 좋게 보이는 문제. 1차 실험에 이 문제가 있었다(§2). |
| **epoch** | 학습 데이터 전체를 한 번 다 보는 것. 이 실험은 3 epoch 학습한다. |
| **seed (랜덤 시드)** | 가중치 초기화와 데이터 순서 같은 무작위성을 정하는 숫자. seed만 바꿔도 결과가 달라지므로 여러 seed로 반복해야 결과가 우연인지 판단할 수 있다. |
| **찍기 점수 (chance level)** | 보기 중 아무거나 골랐을 때의 기대 점수. 2지선다는 50%, 4지선다는 25%다. CV-Bench 공식 식에 넣으면 **42.49점**이다. |

### 1.4 통계 용어

| 용어 | 설명 |
|---|---|
| **평균 ± 표준편차** | seed 여러 개의 평균 점수와 seed 간 흩어짐 정도. 표준편차가 클수록 결과가 seed에 따라 많이 흔들린다는 뜻이다. |
| **오차 범위** | 실험을 다시 했을 때 우연만으로 생길 수 있는 점수 변동 폭. 두 조건의 차이가 이보다 작으면 "의미 없는 차이"로 본다. |
| **학습 오차 / 테스트셋 표본 오차** | 학습 오차는 seed에 따라 학습 결과가 달라지는 변동이다. 테스트셋 표본 오차는 문항 수가 유한해서(2,638개) 생기는 측정 변동으로, 실행 1회 기준 약 ±0.9점이다. |
| **p-value (p값)** | "실제로는 차이가 없다"고 가정했을 때 관측된 정도의 차이가 우연히 나올 확률. 보통 **p < 0.05**면 통계적으로 유의하다고 본다. |
| **Welch t-test** | 두 그룹의 평균이 다른지 검정하는 방법. 두 그룹의 분산이 달라도 쓸 수 있다. 여기서는 seed별 점수 8개 대 8개를 비교한다. |
| **Mann-Whitney U 검정** | 정규분포를 가정하지 않고 두 그룹의 순위로 비교하는 비모수 검정. t-test 결과를 교차 확인하는 데 쓴다. |
| **McNemar 검정** | 같은 문항에 대해 "A만 맞힘"과 "B만 맞힘"의 개수를 비교하는 짝지은 검정. |
| **Bootstrap** | 가진 데이터를 복원추출로 수천 번 다시 뽑아 통계량의 분포를 추정하는 방법. 여기서는 **seed와 문항을 동시에** 다시 뽑아(10,000회) 학습 오차와 테스트셋 오차를 함께 반영한다. |
| **95% 신뢰구간 (95% CI)** | 진짜 차이가 있을 법한 범위. **구간이 0을 포함하지 않으면** 차이가 오차 범위를 벗어난다고 본다. |
| **P(Δ ≤ 0)** | bootstrap에서 RGB-D가 RGB보다 낫지 않게 나온 비율. 작을수록 RGB-D가 낫다는 근거가 강하다. |
| **Cohen's d (효과 크기)** | 두 평균의 차이를 표준편차 단위로 나타낸 값. 0.2는 작음, 0.5는 중간, 0.8 이상은 큼으로 본다. |

## 2. 배경: 왜 이 실험을 다시 했나

### 2.1 1차 실험 (자체 공간 QA)

처음에는 ImageNet 이미지에 DA3 depth로 **자체 공간 QA**를 만들어 비교했다(`depth_ab_study/results/`). 문항 유형은 좌우 비교, 중앙 비교, 위아래 비교였다.

| 인코더 | 전체 정확도 (`results.json`) |
|---|---|
| RGB | 74.05% |
| RGB-D | 98.02% |

> 참고: 1차 실험 커밋 메시지의 수치(RGB 78.6 / RGB-D 98.7)는 같은 설정으로 한 번 더 돌린 실행의 결과다. 저장된 `results.json`은 두 번째 실행 값이다. RGB가 실행에 따라 4.5%p 흔들린 것이 이번 실험에서 seed를 여러 개 돌린 이유 중 하나다.

### 2.2 1차 실험의 문제

1. **데이터 누출**: 정답("어느 쪽이 더 가까운가")을 DA3 depth로 만들었는데, RGB-D 인코더의 4번째 입력 채널도 **같은 DA3 depth**였다. RGB-D는 사실상 정답을 입력으로 받은 셈이라 98%라는 수치를 공간 이해 능력으로 해석할 수 없다.
2. **비공식 평가**: 직접 만든 문항이라 다른 연구와 비교할 수 없고 신뢰도가 떨어진다.

### 2.3 이번 실험의 해결책

- **공인 벤치마크 CV-Bench**로 평가한다.
- CV-Bench 정답은 사람 주석(COCO, ADE20K)과 **3D 센서·주석 박스**(Omni3D)에서 나온다. DA3와 **완전히 독립적**이므로 누출이 없다.
- 학습 문항도 COCO 주석과 SUN RGB-D 3D 박스로 만들어 DA3와 무관하다.

## 3. 실험 설계

### 3.1 모델

```
이미지(224×224) ──► ViT-Base/16 (Frozen) ──► 196×768 ──► MLP Projector (학습) ──► 196×896 ─┐
                                                                                          ├─► Qwen2.5-0.5B-Instruct (Frozen) ──► 답 문자(A/B/…)
질문 텍스트 ───────────────────────────────────────────────────────────────► 토큰 임베딩 ─┘
```

| 구성 | RGB 조건 | RGB-D 조건 |
|---|---|---|
| ViT 입력 | RGB 3채널 | RGB 3채널 + DA3 depth 1채널 |
| ViT 가중치 | `checkpoints/final_model/best_vit_imagenet_1k.pth` | `checkpoints/depth_final_model/best_vit_depth.pth` |
| ImageNet Top-1 | 78.82% | 70.58% |
| Projector | 2-layer MLP 768→896→896 (1,492,736 params, 학습) | 동일 |
| LLM | Qwen2.5-0.5B-Instruct (Frozen) | 동일 |

- depth 채널 전처리: 이미지별로 `d / max(d)`로 정규화한 뒤 `(d − 0.5) / 0.5`로 [-1, 1] 범위로 맞춘다. ImageNet Depth ViT 학습 때와 같은 방식이다.
- RGB-D 조건은 **테스트 때도** DA3로 추정한 depth를 입력받는다. 실제로 쓸 때와 같은 조건이다.
- depth 맵은 박스가 그려진 이미지 그대로에서 추정했다. 테스트 이미지와 같은 조건이다.

### 3.2 학습 데이터 (직접 생성, 43,538문항)

CV-Bench는 test split만 공개되어 있다. 그래서 **벤치마크를 만든 방식을 그대로 따라** 학습 문항을 생성했다(`build_data.py`). 질문 템플릿, 보기 형식, 박스 색(빨강·파랑·초록), 선 두께를 CV-Bench와 같게 맞췄다.

| 과제 | 출처 | 문항 수 | 생성 규칙 |
|---|---|---|---|
| Count | COCO train2017 | 12,000 | 크라우드 박스나 아주 작은 인스턴스(면적 0.2% 미만)가 섞인 클래스는 제외한다. 정답은 1~10. 보기는 4~6개로, "0" + 정답을 포함한 연속 숫자 구간이다. |
| Relation | COCO train2017 | 12,000 | 이미지에 1개만 있고 면적 1% 이상인 물체 쌍만 쓴다. 두 박스가 좌우 또는 상하로 **겹치지 않는** 축에서만 문항을 만들고, 정답은 박스 중심으로 비교한다. |
| Depth | SUN RGB-D train | 10,881 | 3D 박스 중심의 카메라 깊이(z)로 정답을 정한다. 깊이 차가 `max(0.3m, 15%)` 이상인 쌍만 쓴다. |
| Distance | SUN RGB-D train | 8,657 | 3D 박스 중심 간 유클리드 거리로 정답을 정한다. 거리 차가 `max(0.3m, 20%)` 이상인 3개 조합만 쓴다. |

- COCO의 한 이미지는 Count와 Relation 중 한 과제에만 쓴다.
- SUN RGB-D 3D 박스는 카메라 내부·외부 파라미터로 이미지에 투영했다. 이미지 안에 60% 이상 보이고 면적 1% 이상인 물체만 쓴다. 클래스명은 CV-Bench(Omni3D) 표기에 맞췄다(예: `night_stand` → `night stand`).
- 이미지 장축은 640px로 줄였다.
- 2지선다 과제는 정답 위치(A/B)가 거의 50:50이 되도록 균형을 맞췄다.
- 학습셋의 3%(1,306문항)를 고정 seed로 떼어 **검증셋**으로 쓴다. 실제 학습 문항은 42,232개다.

### 3.3 평가 데이터 (CV-Bench test, 2,638문항)

| 구분 | 출처 | Count | Relation | Depth | Distance | 계 |
|---|---|---|---|---|---|---|
| 2D | ADE20K val | 342 | 291 | – | – | 633 |
| 2D | COCO val2017 | 446 | 359 | – | – | 805 |
| 3D | Omni3D (Hypersim / SUNRGBD / nuScenes 각 400) | – | – | 600 | 600 | 1,200 |

**공식 점수 식**:

```
CV-Bench = ½ × ( (acc_2D_ADE20K + acc_2D_COCO) / 2  +  acc_3D_Omni3D )
```

### 3.4 프롬프트와 채점

```
[이미지 토큰 196개]
Question: {CV-Bench prompt (질문 + 보기)}
Answer with the option's letter from the given choices directly.
Answer:
```

- 학습 목표: `" A"` + EOS 토큰이다. 답 토큰에만 loss를 건다.
- 채점: `Answer:` 바로 다음 위치에서 보기 문자 로짓의 argmax를 답으로 본다. 보기가 n개면 A부터 n번째 문자까지만 후보로 둔다.

### 3.5 학습 설정

| 항목 | 값 |
|---|---|
| Epoch | 3 |
| 배치 | 16 × gradient accumulation 2 = 실효 32 |
| Optimizer | AdamW (lr 2e-4, weight decay 0.05) |
| Scheduler | Linear warmup 3% → Cosine decay |
| Gradient clipping | 1.0 |
| 정밀도 | bf16 autocast (Projector 가중치는 fp32) |
| Seed | 0–7 (인코더당 8개) |
| 하드웨어 | NVIDIA RTX 3080 Laptop (8GB), 실행 1회 약 55분 |
| 소프트웨어 | PyTorch 2.10.0 + CUDA 12.6, Transformers 4.57.6 |

- 8GB VRAM에서 어휘 15만 개 크기의 로짓을 모든 위치에 계산하면 메모리가 부족하다. 그래서 `lm_head`는 loss와 채점에 필요한 위치에만 적용한다.

### 3.6 데이터 확보 과정의 검증

- Omni3D 공식 서버는 TLS 인증서가 만료되어 있었다. 보안 검증을 우회하지 않고, Omni3D의 원천인 **SUN RGB-D 원본 3D 주석**을 대신 썼다.
- SUN RGB-D 공식 서버가 너무 느려(약 20KB/s) Hugging Face 미러에서 받았다. 미러 파일이 공식본과 같은지 두 가지로 확인했다.
  - zip **central directory 66MB**(모든 파일의 CRC 포함)를 공식 서버와 바이트 단위로 비교해 일치했다.
  - 압축을 풀면서 CRC를 검사했고 오류는 0건이었다.
- 학습 split(`allsplit.mat`의 `alltrain`)과 CV-Bench SUN 테스트 이미지가 겹치지 않음을 assert로 확인했다.
- 생성한 학습 이미지를 직접 열어 박스 위치와 정답이 맞는지 확인했다.

## 6. 해석

### 6.1 depth 정보가 도움이 되는 과제와 아닌 과제

| 과제 | 효과 | 해석 |
|---|---|---|
| **Depth** (카메라 거리 순서) | **+6.6 (확실)** | depth 채널은 픽셀마다 카메라로부터의 거리를 직접 담고 있다. 두 박스 영역의 depth 값만 비교하면 되는 과제라 가장 직접적인 이득을 본다. seed 간 편차도 작다. |
| **Relation** (좌우·상하 위치) | **+4.1 (확실)** | 위치 관계 자체는 2D 정보라 depth가 필요하지 않다. depth 맵이 **물체 경계와 전경·배경을 구분하는 단서**를 줘서 박스 안 물체와 기준 물체를 더 잘 찾는 것으로 추정한다. 이 메커니즘은 검증하지 않았다. |
| Count (개수 세기) | +0.3 (없음) | 개수를 세려면 개별 인스턴스를 구분해야 하는데, depth 맵만으로는 같은 거리에 붙어 있는 물체를 나누기 어려운 것으로 추정한다. 두 인코더 모두 약 60점으로 이 구성의 한계로 보인다. |
| Distance (물체 간 3D 거리) | −1.7 (없음) | 물체 사이의 3D 거리를 알려면 depth와 이미지상 위치를 함께 써서 3D 좌표를 **계산**해야 한다. frozen 0.5B LLM과 작은 Projector로는 이 계산을 배우기 어렵다. 두 인코더 모두 약 59점으로 찍기(50)보다 조금 높은 수준에 머문다. |

### 6.2 분포 밖(out-of-domain)에서 이득이 크다

- **nuScenes(실외 도로)** 는 학습에 전혀 없던 장면이다. 여기서 RGB-D가 **+6.2** 높다. RGB는 57.9점으로 찍기에 가깝다.
- 반대로 학습 분포와 같은 **검증셋**에서는 RGB-D의 이점이 없다(Depth 90.1 vs 88.3).
- 해석: 같은 분포에서는 RGB만으로도 "실내에서 이런 물체는 대개 가깝다" 같은 단서를 충분히 학습한다. 하지만 처음 보는 장면에서는 그런 단서가 통하지 않는다. 이때 장면과 상관없이 일관된 깊이 정보를 주는 DA3 depth 채널이 **일반화**를 돕는다.
- **Hypersim**(합성 실내)에서는 차이가 없다(−1.9, 유의하지 않음). 합성 이미지 특성 때문인지는 이 실험만으로 알 수 없다.

### 6.3 ImageNet 분류 성능과 공간 이해는 다르다

Depth ViT는 ImageNet 분류에서 RGB ViT보다 **8.2%p 낮다**(70.58 vs 78.82). 그런데 VLM의 공간 이해 벤치마크에서는 오히려 **높다**. 분류 성능만으로 인코더를 고르면 공간 추론에 유리한 인코더를 놓칠 수 있다.

## 7. 한계와 주의점

1. **"센서 depth"가 아니라 "DA3 파이프라인"의 효과다.** RGB-D 조건은 테스트 때도 DA3가 추정한 depth를 받는다. 따라서 이 결과는 DA3 모델을 함께 쓰는 것의 효과이고, DA3의 성능에 좌우된다.
2. **DA3 학습 데이터와 테스트 분포가 겹칠 수 있다.** DA3가 Hypersim이나 nuScenes 같은 데이터로 학습되었을 가능성을 배제하지 못했다. 그렇더라도 CV-Bench **정답**은 3D 주석에서 나오므로 1차 실험 같은 정답 누출은 없다.
3. **절대 점수는 공개 VLM과 비교할 수 없다.** 0.5B LLM에 Projector만 학습했고, ImageNet 분류로만 학습한 ViT를 썼으며, 학습 문항도 CV-Bench와 같은 템플릿으로 직접 만들었다. 이 실험의 의미는 **두 인코더의 상대 비교**에 있다.
4. **하나의 설정에서 얻은 결과다.** LLM까지 미세조정하거나 더 큰 LLM을 쓰거나 다른 Projector를 써도 같은 차이가 유지되는지는 확인하지 않았다.
5. **인코더 자체의 학습 품질이 다르다.** Depth ViT는 ImageNet 정확도가 더 낮다. 같은 품질의 인코더였다면 차이가 더 커지거나 작아질 수 있다.
6. **출처별 분석은 표본이 작다.** 출처당 400문항이라 Hypersim이나 SUNRGBD 단위의 결론은 약하다.

## 10. 향후 과제

- **LLM 미세조정(LoRA 등)**: Projector만이 아니라 LLM도 학습하면 Distance처럼 계산이 필요한 과제에서 depth 정보를 활용하게 되는지 확인한다.
- **센서 depth와 비교**: SUN RGB-D 센서 depth를 입력으로 쓰는 조건을 추가해 DA3 추정 오차의 영향을 분리한다.
- **품질을 맞춘 인코더**: ImageNet 정확도가 비슷한 RGB·RGB-D 인코더로 다시 비교한다.
- **Relation 향상의 메커니즘 분석**: attention 시각화나 depth 채널 제거(ablation)로 위치 관계 이득이 어디서 오는지 확인한다.
- **다른 공간 벤치마크**: BLINK, SpatialBench, What'sUp 등에서도 같은 경향이 나오는지 확인한다.
